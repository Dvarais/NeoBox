**Инициатор:** Аудит безопасности после инцидента со стилером

## 📋 Резюме выполненных исправлений

### ✅ Исправление #1: Шифрование учётных данных на диске (CRITICAL)
**Файлы:** `backend/storage/storage.go` (новый), `backend/security/encryption.go`, `backend/service/service.go`, `main.go`

**Изменения:**
- Ключ AES-256 защищается через `CryptProtectData`/`CryptUnprotectData` (Windows DPAPI)
- `SecureWipe()` очищает ключ из памяти при закрытии, `LockMemory()` не даёт выгрузить его в файл подкачки
- **`subscriptions.json` шифруется на диске** (AES-256-GCM, конверт `NBOX\x01`) — там лежат полные прокси-ссылки с UUID и паролями
- Плейнтекстовый файл от старых сборок мигрируется автоматически при старте
- Запись атомарная (temp + fsync + rename), файл, который не удалось расшифровать, не перезаписывается, а сохраняется как `.unreadable-<время>`
- `settings.json` намеренно остаётся plain JSON: секретов не содержит, правится вручную

**⚠️ История:** в редакции 1.6.3.7 этот пункт был заявлен выполненным, но модуль шифрования не был подключён —
`InitEncryption()` не вызывался, `Encrypt`/`Decrypt` не имели ни одного call-site, и подписки лежали в открытом
виде с правами `0644`. Фактически исправлено в 1.7.5.

**До:** `subscriptions.json` — plaintext, все учётные данные серверов читаются стилером напрямую  
**После:** AES-256-GCM под DPAPI-ключом + locked memory + secure wipe + атомарная запись

### ✅ Исправление #2: Проверка подписи обновлений (HIGH)
**Файлы:** `backend/security/signature.go` (новый), `backend/service/service.go`

**Изменения:**
- Модуль `security/signature.go` для Ed25519 проверки подписей
- **Проверка обязательна (fail-closed).** Пустая или некорректная подпись отклоняется до начала загрузки
- **`CheckUpdates` не публикует `downloadUrl`, если у релиза нет валидного `.sig`-ассета** — фронтенд в этом случае просто открывает страницу релиза для ручной загрузки
- URL установщика **и** URL подписи проходят одну проверку: HTTPS + только домены GitHub (`validateUpdateURL`)
- Загрузка идёт в свежий каталог со случайным именем (`os.MkdirTemp`) с урезанным DACL вместо предсказуемого `%TEMP%\neobox_update.exe`
- Лимит размера загрузки 256 МБ, с проверкой и заявленного `Content-Length`, и фактически записанных байт
- При любой ошибке весь каталог удаляется — исполняемого файла не остаётся

**⚠️ История:** в редакции 1.6.3.7 проверка была fail-open: ветка `if signatureHex != ""` пропускала установку
без подписи, а сам `signatureHex` брался из ответа GitHub API. Атакующему, влияющему на ответ API или на
содержимое релиза, достаточно было не публиковать `.sig`, чтобы проверка отключилась целиком. Исправлено в 1.7.5.

**До:** Проверялся только домен GitHub URL, подпись опциональна  
**После:** Ed25519 подпись обязательна; без неё установка внутри приложения недоступна

**Ключи:** публичный ключ уже прописан в `PublicKeyHex`. Приватный хранить офлайн, подписывать релизы через
`go run ./cmd/sign -key <hex> -file NeoBox_Setup.exe` и публиковать полученный `.sig` рядом с установщиком —
**без него автообновление у пользователей работать не будет.**

### ✅ Исправление #2b: Системный прокси пользователя (HIGH)
**Файлы:** `backend/service/service.go`, `backend/storage/storage.go`, `main.go`

**Изменения:**
- Бэкап прокси-конфигурации пользователя **сохраняется на диск** (`proxy-backup.json`, атомарная запись), а не только в память процесса
- При старте бэкап поднимается в `NewAppService` — сессия, упавшая с установленным прокси, теперь восстановима
- Без бэкапа настройка сбрасывается **только если она всё ещё указывает на NeoBox**; чужой прокси не трогается
- Первый захват выигрывает: переподключения watchdog не затирают исходное значение пользователя
- Бэкап, указывающий на сам адрес NeoBox, отклоняется — иначе браузеры остались бы на мёртвом loopback-порту

**До:** `SetSystemProxy(false)` при каждом старте безусловно писал `ProxyEnable=0`, выключая прокси любого
пользователя, у которого он был настроен. Бэкап жил только в памяти, поэтому «очистка после краха» физически
не могла ничего восстановить.  
**После:** чужая конфигурация не затрагивается, своя — восстанавливается даже после аварийного завершения

### ✅ Исправление #2c: Kill Switch — восстановление и ошибки (MEDIUM)
**Файлы:** `backend/security/scheduler.go`, `backend/service/service.go`, `backend/service/diagnostics.go`

**Изменения:**
- Факт установки правил фиксируется маркером `killswitch.active`; при старте оставшиеся после краха
  правила удаляются автоматически. Если удалить не удалось (нет прав) — маркер сохраняется для повтора,
  а в диагностику добавляется явный пункт с указанием, что делать
- `netsh` больше не выполняется вслепую: ошибки возвращаются с текстом вывода команды
- Факт удаления проверяется через `netsh ... show rule` по коду возврата — способ, не зависящий от локали
  (у `delete` код возврата одинаков для «правила нет» и «отказано в доступе»)
- Права администратора проверяются **до** подключения (как для TUN), пользователь получает штатный UAC
- Сбой постановки Kill Switch отменяет подключение и откатывает уже созданные правила
- Kill Switch не ставится, если адрес VPN-сервера не удалось получить: block-all без исключения для сервера
  рвёт сам туннель, после чего снять правило уже некому
- Адреса из fake-IP диапазона `198.18.0.0/15` отклоняются как исключения: при включённом FakeDNS резолв
  внутри процесса отвечает через туннель, и в исключения попал бы синтетический адрес вместо реального сервера

**До:** правила переживали крах, оставляя машину без интернета без видимой причины; все ошибки `netsh`
игнорировались, поэтому Kill Switch мог не примениться (например, без прав администратора), а интерфейс
показывал его включённым  
**После:** правила снимаются при следующем запуске, сбой постановки виден и отменяет подключение

### ✅ Исправление #3: Устранение TOCTOU race condition (MEDIUM)
**Файлы:** `backend/service/service.go`

**Изменения:**
- Удалена отдельная проверка порта 20809 (`net.Listen` → `ln.Close()`)
- sing-box теперь bind'ит порт напрямую
- Ошибка "address already in use" обрабатывается после попытки запуска

**До:** Race window между проверкой и использованием порта  
**После:** Атомарная проверка+bind внутри sing-box

### ✅ Исправление #4: Убран hardcoded fallback secret (MEDIUM)
**Файлы:** `backend/service/service.go`, `backend/service/vpn.go`

**Изменения:**
- Удалена строка `"neobox-secure-fallback-clash-secret"`
- Фолбэка нет вообще: `generateClashSecret` возвращает ошибку, а `StartXray` отменяет подключение
  и показывает её пользователю. Подключаться без секрета нельзя — Clash API остался бы открыт
  для любого локального процесса
- В редакции 1.6.3.7 здесь стоял `panic()`, ронявший весь клиент. Отказ в подключении даёт
  тот же результат по безопасности, но пользователь видит причину вместо исчезнувшего окна

**До:** Предсказуемый секрет был скомпилирован в бинарник и извлекался из него  
**После:** Секрет только случайный; при отказе RNG подключение отменяется с внятной ошибкой

### ✅ Исправление #8: CSP в frontend (LOW)
**Файлы:** `frontend/index.html`, `frontend/lib/jsQR.js` (новый)

**Изменения:**
- jsQR вендорится локально, `https://unpkg.com` удалён из CSP `script-src`
- SRI hash на теге: `sha256-vEDIoVGWI2sjFNsIVvcsoLSZgM1UE7jIUqc0n1/uCFk=`
- Файл лежит в `frontend/public/lib/jsQR.js` — vite копирует `public/` в `dist/` как есть
- Из `script-src` убран хэш-источник: CSP-хэши авторизуют только инлайновые скрипты,
  которых в проекте нет; SRI-хэш файла в `script-src` не давал ничего и лишь выглядел так,
  будто даёт. Все скрипты покрыты `'self'`

**⚠️ История:** в редакции 1.6.3.7 файл лежал в `frontend/lib/`, откуда vite его не копировал
(`public/` — единственный каталог, копируемый как есть). В `dist/` его не было, `dist` вшивается
через `go:embed`, поэтому в релизной сборке QR-сканер не работал вообще: срабатывала ветка
`console.error("jsQR is not loaded yet")`. Исправлено в 1.7.5.

**Примечание про `style-src`:** `'unsafe-inline'` там **остаётся** (вопреки прошлой редакции этого
документа). UI повсеместно присваивает `element.style` / `cssText`, поэтому убрать его можно только
после рефакторинга этих мест.

**До:** Внешний скрипт с CDN; после вендоринга — скрипт, не попадавший в сборку  
**После:** Локальный скрипт с integrity check, реально присутствующий в `dist/`

## 🛡️ Дополнительные защитные механизмы

### ❌ Anti-Tampering модуль — удалён в 1.7.5
**Файл:** `backend/security/antitamper.go` (удалён)

Модуль был удалён целиком: ни одна из его защит не работала, а часть активно вредила.

- `VerifyBinaryIntegrity()` — **неосуществим по построению.** Хэш бинарника нельзя вшить в этот же
  бинарник: вшивание меняет хэш. Плюс self-check не является защитой — атакующий, правящий бинарник,
  правит и проверку. Плюс читал весь `.exe` (сотни МБ вместе с sing-box) в память на старте.
  Константа `expectedBinaryHash` всегда была пустой, то есть проверка не выполнялась ни разу.
- `DetectSuspiciousEnvironment()` — заглушка: объявляла список из 12 процессов и делала
  `_ = suspiciousProcesses`. Возвращала `true` только при одном ядре CPU. Не вызывалась ниоткуда.
- `IsDebuggerPresent()` / `CheckRemoteDebuggerPresent()` + `SecureStartup()` — обход занимает минуты,
  а цена высокая: `os.Exit(1)` без сообщения в UI (stderr уже перенаправлен в `crash.log`), то есть
  для пользователя окно просто исчезало. Для опенсорсного клиента защита от отладки бессмысленна:
  исходники и так открыты.

**Что сохранено:** `LockMemory()` / `UnlockMemory()` (VirtualLock) — единственное, что делало реальную
работу. Переехали в `encryption.go`, к своему единственному потребителю: не дают ключу шифрования
попасть в `pagefile.sys`, откуда он пережил бы завершение процесса.

**Замена:** настоящая гарантия целостности даётся Authenticode-подписью `.exe`, которую проверяет сама
Windows, а не самодельными проверками внутри процесса.

## ⚠️ Действия required перед следующим релизом

1. **Генерация Ed25519 ключей:**
   ```go
   pub, priv, _ := security.GenerateSigningKeys()
   fmt.Println("Public:", pub)   // Вставить в signature.go
   fmt.Println("Private:", priv) // Хранить офлайн!
   ```

2. **Подпись установщика — обязательна.** Без `.sig` рядом с установщиком автообновление
   у пользователей 1.7.5+ работать не будет (fail-closed, см. исправление #2):
   ```bash
   wails build -tags with_utls,with_clash_api,with_quic,with_wireguard,with_gvisor
   go run ./cmd/sign -key <приватный_ключ_hex> -file NeoBox_Setup_v1.7.5.exe
   ```
   Имя ассета должно быть ровно `<имя установщика>.exe.sig` — поиск идёт по точному совпадению.

3. **Закоммитить `frontend/public/lib/jsQR.js`** — файл не отслеживается git, без него
   QR-сканер не соберётся из чистого клона.

## 🎯 Рекомендации для будущей защиты

1. **Code signing сертификат** — подписывать `.exe` через EV certificate. Это единственная проверка
   целостности, которую выполняет сама ОС, и она же снимает предупреждения SmartScreen
2. **CI с `golangci-lint` и `go test -race`** — пять находок аудита 1.7.5 (`gofmt`, мёртвый код,
   проглоченные ошибки, битая build-директива) линтер находит бесплатно на каждом коммите
3. **Regular audits** — проводить аудит безопасности каждый релиз

**Не рекомендуется** (было в редакции 1.6.3.7): обфускация, runtime packing и телеметрия попыток
отладки. Для опенсорсного VPN-клиента обфускация и упаковка не дают защиты (исходники открыты),
но резко повышают вероятность ложных срабатываний антивирусов — той самой проблемы, ради которой
в `scheduler.go` правила брандмауэра снабжены человекочитаемым описанием. Телеметрия попыток отладки
противоречит назначению продукта.
